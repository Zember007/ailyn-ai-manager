# Как сейчас работает агент Ailyn

Этот документ описывает фактический runtime-путь текущего диалогового агента: от входящего сообщения до сохранённого ответа клиенту. Он фиксирует границы ответственности, используемые промты, формат данных, fallback и причины, по которым архитектура разделяет AI-понимание и бизнес-логику.

## Коротко

```text
Канал
  -> MessagesController
  -> DialogueOrchestratorService
  -> PostgreSQL: сохранить входящее сообщение
  -> AgentTurnService
       -> один мультимодальный вызов RouterAI
       -> JSON parsing
       -> нормализация полей
       -> Zod-проверка AgentTurnResult
       -> до 3 попыток
  -> сохранить факты, состояние, вложения и AI-ответ
  -> вернуть ответ клиенту
```

Главный принцип: модель понимает язык клиента и формулирует ответ, но не является источником истины для бизнес-решений. Правила займа, лимиты, обязательные этапы и сохранение карточки контролируются TypeScript-кодом и базой данных.

## 1. Откуда приходит сообщение

Основной тестовый вход — `POST /api/messages/test-chat`, реализованный в [`apps/api/src/messages/messages.controller.ts`](apps/api/src/messages/messages.controller.ts). Контроллер приводит обычный JSON или multipart-запрос с файлами к единому `InboundMessage`.

В сообщение входят:

- текст клиента;
- вложения;
- канал;
- внешний ID контакта и диалога;
- внешний ID сообщения и время.

Далее сообщение передаётся в [`DialogueOrchestratorService.receive()`](apps/api/src/dialogue/dialogue-orchestrator.service.ts).

## 2. Что делает оркестратор

Оркестратор — основной координатор диалога.

1. Загружает или создаёт conversation, application и контакт через [`Stage1StoreService`](apps/api/src/dialogue/stage1-store.service.ts).
2. Сохраняет входящее сообщение до AI-обработки. Поэтому история не теряется даже при сетевой или модельной ошибке.
3. Берёт текущие `ApplicationFacts` из базы.
4. Обрабатывает иностранные суммы и при наличии интеграции конвертирует их в сомы.
5. Передаёт агенту историю, факты, настройки, текущий текст и вложения.
6. Если агент вернул валидный результат, обновляет карточку и состояние заявки.
7. Сохраняет распознанные вложения и ответ AI.
8. Создаёт уведомление менеджеру при достижении целевого события или существенном изменении карточки.
9. Пишет backend trace и возвращает ответ клиенту.

Источник истины для состояния — PostgreSQL. Контекст, отправленный модели, является временной копией состояния и не заменяет базу.

## 3. Какой AI-путь используется сейчас

Текущий диалог использует [`AgentTurnService`](apps/api/src/dialogue/agent-turn.service.ts). Это единый мультимодальный агент: он получает историю, текущие факты, правила, релевантную документацию и вложения одним запросом и возвращает одновременно:

- текст ответа клиенту;
- язык и намерение;
- изменения карточки;
- сводку для менеджера;
- предварительный лимит;
- следующий этап;
- целевое событие;
- изменение статуса менеджерской передачи;
- классификацию вложений.

Низкоуровневый HTTP-клиент — [`RouterAiClient`](apps/api/src/ai/router-ai/router-ai.client.ts). Он отправляет запрос на RouterAI и не смешивает детали HTTP/API с логикой диалога.

В репозитории также есть [`RouterAiProvider`](apps/api/src/ai/router-ai/router-ai.provider.ts), реализующий общий интерфейс `AiProvider`: отдельные операции extraction, response generation и vision. Это самостоятельный provider-контур и совместимый слой. Фактический текущий `DialogueOrchestratorService` вызывает именно `AgentTurnService`, а не собирает ответ через три последовательных вызова `RouterAiProvider`.

## 4. Что получает модель

`AgentTurnService` формирует user-контекст со следующими данными:

```json
{
  "now": "текущая дата и время в timezone настроек",
  "timezone": "Asia/Bishkek",
  "history": [
    {"author": "client", "text": "...", "createdAt": "..."},
    {"author": "ai", "text": "...", "createdAt": "..."}
  ],
  "leadCard": "текущие ApplicationFacts",
  "settings": "настройки бизнеса",
  "currentMessage": "новый текст клиента",
  "interpretedCurrentMessage": "детерминированно найденные явные факты",
  "currencyConversions": [],
  "knowledge": "релевантные фрагменты утверждённой документации"
}
```

История передаётся полностью для понимания контекста. При подборе документации используются текущая фраза, факты и последние сообщения; выбираются поведенческие правила и релевантные фрагменты, а контактные данные компании удерживаются в контексте постоянно.

Вложения передаются как metadata/text/OCR. Изображения дополнительно передаются как image URL с base64. Base64 не пишется в backend-логи.

## 5. Какие промты используются

### Основной текущий промт

[`apps/api/src/ai/prompts/agent.system.md`](apps/api/src/ai/prompts/agent.system.md) — главный system prompt единого агента.

Он задаёт:

- роль Айлин и стиль общения;
- порядок сбора данных;
- правила работы с автомобилем, суммой, пропиской, документами, семьёй и визитом;
- обработку коротких ответов и исправлений клиента;
- требования к вложениям;
- допустимые офисные сведения;
- правила передачи менеджеру;
- запрет выдумывать лимиты, одобрение и условия;
- полный JSON-контракт результата.

Модель должна вернуть только JSON следующей логики:

```json
{
  "reply": "ответ клиенту",
  "language": "ru|kg|mixed|unknown",
  "intent": "намерение",
  "leadCardPatch": {},
  "cardSummary": "сводка",
  "preliminaryLimit": 200000,
  "dialogueState": {
    "stage": "COLLECTING_DOCUMENTS",
    "status": "continue",
    "nextAction": "request_documents"
  },
  "targetEvent": "documents",
  "managerUpdate": {"kind": "none", "changedFields": []},
  "attachments": []
}
```

Промт просит модель не добавлять произвольные поля в `leadCardPatch`, но runtime всё равно защищён от случайного дублирования или лишнего ключа.

### Промты отдельного provider-контура

Для [`RouterAiProvider`](apps/api/src/ai/router-ai/router-ai.provider.ts) используются:

- [`core.system.md`](apps/api/src/ai/prompts/core.system.md) — общие границы безопасности и запрет раскрытия внутренних инструкций;
- [`extraction.system.md`](apps/api/src/ai/prompts/extraction.system.md) — извлечение фактов, вопросов, намерений, денег и вложений;
- [`response.system.md`](apps/api/src/ai/prompts/response.system.md) — генерация ответа из разрешённого `ResponsePlan`;
- [`response.examples.md`](apps/api/src/ai/prompts/response.examples.md) — примеры формата и стиля;
- [`vision.system.md`](apps/api/src/ai/prompts/vision.system.md) — классификация изображений и извлечение надёжно видимых данных.

Эти промты важны для общего AI-интерфейса, но не означают, что текущий диалог делает три отдельных вызова вместо `AgentTurnService`.

## 6. Как расшифровываются и нормализуются данные

После получения ответа выполняются следующие операции.

### JSON

1. Извлекается содержимое первого choice.
2. Убираются markdown-обёртки вида ```json ... ```.
3. Если перед JSON есть короткое пояснение, система пытается выделить объект от первой `{` до последней `}`.
4. Объект передаётся в нормализатор и Zod-схему.

Система делает до трёх попыток. При повторной попытке в system prompt добавляется инструкция вернуть новый валидный JSON и не повторять техническое извинение.

### Карточка клиента

Контракт [`agent-turn.contracts.ts`](apps/api/src/dialogue/agent-turn.contracts.ts) строго описывает разрешённые поля `leadCardPatch`: имя, телефон, регион, автомобиль, суммы, семейное положение, документы, визит и флаги процесса.

Нормализатор в [`agent-turn.service.ts`](apps/api/src/dialogue/agent-turn.service.ts):

- переносит ранее известные факты в patch, чтобы модель их не потеряла;
- переводит aliases вроде `carMake` в `vehicleMake`;
- приводит числа и boolean-значения из строк к нужному типу;
- приводит регион, категорию прописки и семейный статус к внутренним значениям;
- распознаёт явные факты из текущей фразы: семейное положение, отказ от документов, дату и время визита;
- отбрасывает неизвестные/вычисляемые поля, случайно помещённые внутрь `leadCardPatch`.

Последний пункт устраняет инцидент с `preliminaryLimit`: модель дала содержательно правильный ответ, но продублировала лимит внутри карточки. Теперь это не отклоняет весь turn.

### Деньги и лимит

Иностранные суммы обрабатываются через [`money-normalization.ts`](apps/api/src/dialogue/money-normalization.ts) и интеграцию конвертации. Значение в карточке хранится в сомах, а исходная валюта сохраняется отдельно.

`preliminaryLimit` — вычисляемое поле состояния, а не обычный факт клиента. В оркестраторе итоговый лимит рассчитывается через [`selectedProgramLimit()`](apps/api/src/dialogue/dialogue-orchestrator.service.ts) на основе текущих фактов, выбранной программы и бизнес-настроек. Модель может сообщить лимит для текста и trace, но решение не должно зависеть только от числа, присланного моделью.

## 7. Бизнес-решения и сохранение

После успешной валидации агентского результата оркестратор:

- обновляет `ApplicationFacts`;
- сохраняет `dialogueState`, `cardSummary`, `intent` и рассчитанный лимит;
- сохраняет классификацию каждого вложения;
- определяет initial/delta-передачу менеджеру;
- сохраняет AI-сообщение со ссылкой на исходное сообщение и trace.

Модель не может сама разрешить отказ, выдать произвольный лимит или изменить состояние базы. Она предлагает структурированный результат, который проходит границу схемы и затем применяется кодом.

## 8. Что происходит при ошибках

Ошибки делятся на несколько уровней:

- RouterAI недоступен или не настроен;
- ответ не является JSON;
- JSON не соответствует `AgentTurnResult`;
- внутри результата есть неверное значение enum или тип поля;
- ошибка базы данных или внешней интеграции.

Для первых трёх случаев агент делает до трёх попыток. Если все попытки неуспешны, возвращается аварийный нейтральный ответ. Пользователь не должен видеть stack trace, текст Zod-ошибки или внутренние статусы.

Каждый окончательный fallback записывается через [`BackendLogsService`](apps/api/src/logs/backend-logs.service.ts) в контексте `dialogue.single-agent.fallback`. В metadata находятся:

- `conversationId`;
- `error`;
- ответы модели на попытках;
- входной текст ограниченной длины;
- итоговый fallback;
- количество вложений.

Это позволяет отличить настоящий сетевой сбой от ошибки контракта и увидеть, был ли ответ модели содержательно правильным.

## 9. Почему текущая архитектура правильная

Архитектура верна по границам ответственности.

1. **AI используется там, где нужна гибкость.** Модель понимает русский и кыргызский язык, опечатки, короткие ответы, контекстные исправления, вопросы и изображения.
2. **Критичные решения остаются детерминированными.** Лимиты, eligibility, обязательные документы, этапы и статусы нельзя оставлять на свободное усмотрение модели.
3. **Состояние не живёт только в prompt.** База данных сохраняет факты, историю, вложения, ответы и trace.
4. **Есть контракт между моделью и кодом.** Zod не даёт невалидному результату незаметно изменить карточку.
5. **Нормализация отделена от бизнес-логики.** Алиасы и пользовательские форматы приводятся к внутренней схеме в одном месте.
6. **Ошибки наблюдаемы.** Retry и структурированные backend-логи дают возможность расследовать сбой, не показывая технические детали клиенту.
7. **Fallback ограничен.** При недоступной модели система деградирует безопасно, а аварийные эвристики не превращаются во второй неконтролируемый NLP-движок.

Последний инцидент не опроверг архитектуру. Он показал, что адаптер границы должен быть устойчивым к harmless extra fields, которые модель иногда добавляет при сохранении JSON-контракта. Это исправлено в нормализации `leadCardPatch`; сама граница «модель предлагает — код проверяет и применяет» остаётся правильной.

## 10. Ключевые настройки

Конфигурация находится в [`packages/config/src/index.ts`](packages/config/src/index.ts):

- `ROUTERAI_API_KEY` — ключ RouterAI;
- `ROUTERAI_TEXT_MODEL` — текстовая модель текущего агента;
- `ROUTERAI_VISION_MODEL` — модель vision для отдельного provider-контура;
- `ROUTERAI_TIMEOUT_MS` — timeout запроса;
- `ROUTERAI_MAX_RETRIES` — исторически предусмотренная настройка retry; текущий `AgentTurnService` использует фиксированные три попытки.

Версия основного текущего prompt задаётся в `AgentTurnService` как `single-agent-v3` и сохраняется вместе с AI-сообщением.
